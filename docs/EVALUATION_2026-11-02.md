# 定向改稿与质量闭环：20题正式评测

运行日期：2026-11-02（Asia/Shanghai）。真实文本API，非mock。结果源为`evals/results-final-2026-11-02/summary.json`和各任务JSON，人工偏好评价尚未填写。

## 实验口径

- 20个人工构造任务，每类5题：受众语气、结构篇幅、保留原文、组合反馈。
- 基线：提交5838eda中的旧写稿提示，只输入选题、修改意见、修订次数。
- 升级：原始需求、内容要求和原文进入模型；写稿后规则/语义检查，必要时最多自动修改一次。
- 两组使用相同当前模型接入点、温度和关闭思考的推理参数。基线是旧提示的受控对比，不是旧环境的历史重放。运行前试验曾发现开启思考与输出额度组合会导致空稿，已修复，不把此调试结果混入正式统计。
- 任务是已给定原稿和反馈的改稿任务，不包含选题、配图和人工等待时间。每题每组一次，交替两组先后顺序，并发2题。
- 硬规则40项：20项长度、10项指定栏目、10项原样保留案例文本。每题要求不同，因此同时报告“全约束通过任务数”和“检查项通过数”。

## 正式结果

- 两组均20/20完成，无生成失败。升级组26次语义检查均成功返回并通过结构/引用验证。
- 全部硬规则均通过的任务：基线3/20（15%），升级18/20（90%）。
- 硬规则检查项通过：基线13/40（32.5%），升级38/40（95%）。
- 总Token：基线8,965，升级43,107，约4.81倍。均为API返回的用量，不据此推算人民币费用。
- 逻辑模型调用次数：基线20，升级52；升级含20次改稿、26次检查、6次自动修订。
- 单题端到端耗时中位数：基线7.62秒，升级11.10秒。网络、服务端负载和并发会影响结果，非生产P95承诺。

这组结果说明：在明确长度、栏目和保留文本的任务里，额外上下文与检查闭环改善了约束落实，代价是更多调用和Token。不能把90%解释为通用文章质量、事实正确率或所有用户任务的成功率。

## 未通过与停止边界

自动修订上限后仍有两题硬规则不满足，系统交人工审核：

- `preserve_original_01`：175个非空白字符，低于180下限。
- `structure_length_02`：281个非空白字符，高于280上限。

`audience_tone_03`的硬规则通过，但模型语义检查仍建议改善，也在上限后交人工。最终3题仍带修改建议，没有通过隐藏循环把结果强行刷到通过。

## 人工评价与限制

`blind_review.json`提供隐藏版本标签的A/B正文和统一rubric；`blind_key.json`保存映射。当前未填写人工偏好，不声称“人工认可度提升”。

语义检查由同一模型系列完成，并不独立于生成器。它可能漏检或误判，不能替代人工判断；例如示范文章中的虚构个人经历由人工意见进一步删除，说明保留人工审核的必要性。

任务集规模小、由实现者构造，且只做单次采样；没有随机抽取真实业务请求。真实业务上的稳定性、事实质量和更多主题的泛化仍需更大样本验证。该报告适合展示评测方法和边界，简历应写明“固定20例改稿任务的机械约束通过情况”。

## 复现

在项目根目录：

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_revision.py --real --limit 20 --output evals/results-another-run
```

使用不同输出目录保留历史结果。每次调用会产生真实文本API用量，不生成图片。由于模型采样和服务变化，数值不保证逐次一致。输入文件SHA256及模型标识已记录在正式`summary.json`中。
